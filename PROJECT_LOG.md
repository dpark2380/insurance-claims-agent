## Phase 1 — RAG coverage lookup

### PDF text extraction (`code/ingest/extract_text.py`)
**Built:** Loops `data/manifest.json`, pulls per-page text out of each PDS/KFS PDF with `pdfplumber`, writes one JSONL file per doc to `data/extracted/`. Flags (doesn't drop) pages under 40 words as likely covers/TOC.
**Theory:** PDFs have no native "paragraph" structure — a PDF is drawing instructions for glyphs at coordinates. A text extractor has to reconstruct reading order from those coordinates, which is why multi-column layouts can come out garbled.
**Here:** This is the raw material the whole RAG pipeline is built on — 18 policy documents, 705 pages, converted to plain text before anything else can happen.

### Chunking (`code/rag/chunking.py`)
**Built:** `chunk_text` splits text into overlapping 200-word windows (50-word overlap); `chunk_page_records` wraps it to carry doc/page/insurer metadata through.
**Theory:** LLMs and retrieval indexes both need bounded-size text units, not whole documents. Overlap exists so a sentence that straddles a chunk boundary still appears whole in at least one chunk — without it, an answer's evidence can get split in half and neither chunk retrieves well on its own.
**Here:** Produced 1,650 chunks from 705 pages — the actual unit that gets indexed and retrieved.

### Hybrid retrieval index (`code/rag/index.py`)
**Built:** BM25 (keyword ranking) and TF-IDF cosine similarity (vector-style ranking), combined via Reciprocal Rank Fusion (RRF).
**Theory:** BM25 scores documents by term overlap, weighted so rare words matter more than common ones and long documents don't win purely by being long — but it only ever matches exact words. TF-IDF cosine represents each chunk as a vector and measures the angle between it and the query vector, catching some of what BM25 misses but still exact-word-based (no semantic understanding, since this project's TF-IDF isn't a neural embedding). Neither ranking is reliably "the better one" per query, so instead of picking one, RRF merges both ranked lists by rank position (`1/(k+rank)`), not raw score — sidesteps the problem that BM25 and cosine scores live on different, incomparable scales.
**Here:** Every retrieval call runs both rankers and fuses them, so a query that happens to favor exact keyword match (BM25) or vector overlap (TF-IDF) still surfaces good chunks either way.

### The `compute_idf` performance bug (85s → 1s)
**Built:** Fixed `compute_idf` in `index.py` — was 85 seconds to index 1,650 chunks, now ~1 second.
**Theory:** IDF (inverse document frequency) needs, for every vocabulary word, a count of how many documents contain it. The buggy version re-tokenized every one of the 1,650 documents from scratch (`.lower().split()`) for *each* of the ~9,200 vocabulary words, and checked membership with `word in a_list` — a linear scan, not a lookup. That's roughly `vocab × docs × avg_doc_length` word comparisons (~2.3 billion). The fix: tokenize each document into a `set` once, up front, then check membership against those sets (`word in a_set` is O(1) average, not O(length)). Same math, ~80x faster — a textbook case of an accidentally quadratic-ish loop hiding inside what looks like a simple nested `for`.
**Here:** Makes the CLI's "rebuild the index fresh on every question" design (chosen because 1,650 chunks was assumed cheap to index) actually true instead of an 85-second wait per query.

### Metadata-filtered retrieval (`code/rag/retrieve.py`)
**Built:** When `insurer`/`product`/`doc_type` are given, filters the chunk pool *before* ranking, then re-runs BM25 (not the pre-built global BM25) on just the filtered subset.
**Theory:** BM25's IDF weighting is corpus-relative — a word looks "rare" or "common" only relative to whatever set of documents it's being scored against. Filtering to one insurer's chunks *after* ranking against the full 18-document corpus would keep IDF weights computed from the wrong corpus (e.g. "storm" might look rare across all insurers combined but common within one insurer's own documents). Re-indexing BM25 on just the filtered chunks gives IDF numbers that reflect the actual pool being searched.
**Here:** Lets a query like "is storm damage covered?" `--insurer AAMI` search only AAMI's ~300 chunks with accurate term weighting, instead of diluting the ranking with 17 other insurers' vocabulary.

### Grounded generation (`code/rag/generate.py`)
**Built:** System prompt instructs the model to answer *only* from provided excerpts, cite every claim as `[Insurer Product DocType, page N]`, and explicitly say "not enough information" rather than guess. `cache_control: {type: "ephemeral"}` is set on the system prompt.
**Theory:** LLMs will confidently fill gaps with plausible-sounding but ungrounded text ("hallucination") unless explicitly constrained to cite sources and given permission to say "I don't know." Prompt caching works by hashing a prefix of the request (here: the system prompt) — if a later request sends the identical prefix, the API skips reprocessing it and charges a fraction of the normal input-token price for a cache *read* (a first-time cache *write* costs slightly more than normal, but every reuse after that is far cheaper).
**Here:** The system prompt is identical across every question asked in a session, so it's the one piece worth caching in Phase 1; the retrieved context (which changes per question) isn't cached here.

### CLI (`code/cli.py`)
**Built:** Wires retrieval + generation together into `python cli.py "<question>" --insurer X`. Added `python-dotenv` (not in the original build checklist) so `.env` actually gets loaded — the checklist assumed `os.environ` would just see the file, which it doesn't without an explicit loader call.
**Theory:** N/A — this is glue code, not a new concept.
**Here:** The Phase 1 demo target: ask a coverage question, get a cited answer, end to end.

### Workspace-identity-linked API keys (`code/rag/generate.py`)
**Built:** Hit and resolved a real auth error — `anthropic-workspace-id is required when authenticating with an identity-linked API key`. `ANTHROPIC_WORKSPACE_ID` in `.env` wasn't enough on its own: the SDK only auto-attaches it via a separate Bearer-token/WIF credential chain, which a plain `Anthropic(api_key=...)` client never enters. Fix was to read the env var manually and pass it via `default_headers={"anthropic-workspace-id": ...}`.
**Theory:** Some Anthropic API keys are scoped to an organization with multiple workspaces, so a request has to say *which* workspace it's spending against — unrelated to Workload Identity Federation (federated cloud tokens), which doesn't apply to a local script at all. Two different auth code paths in the same SDK can read the same env var differently depending on which one you're on — worth checking the actual client construction path, not just "is the var set."
**Here:** One-line header addition once the actual cause was found; real generation calls now succeed end to end.

### Step 1.7 verification — two real retrieval failures found and handled differently (`code/eval/run_phase1_eval.py`)
**Built:** 9 hand-written coverage questions across 5 insurers, run through retrieval + generation directly, citations checked against the actual source PDF text. 8/9 pass; 1 documented failure.
**Theory:** An eval set's job is to catch failures you can't see by eyeballing one query. It found two different failure *classes*, which need different responses. (1) RAA flood question: the correct chunk was BM25's #1 pick by a wide margin, but fell one spot outside RRF's pre-fusion candidate window (top 15), so it got zero credit from the vector ranker and lost — a real bug, fixed by widening the pool to 30 (a global constant, not conditioned on this query). (2) A RealInsurance malicious-damage question: the correct chunk ranked weakly on *both* rankers because the query says "tenant" and the policy text says "someone who lives in your home" — a literal vocabulary mismatch that keyword-based retrieval (BM25/TF-IDF) cannot bridge structurally, no matter how wide the pool gets. Widening the pool further to force that one case to pass would be tuning a hyperparameter against your own eval set, not fixing anything general — so it's documented as an accepted limitation instead (real semantic embeddings would catch it; that's Phase 6+'s stretch goal, not Phase 1's).
**Here:** This is why the checklist says "failures written down with a reason, not silently ignored" is an acceptable Definition of Done — not every retrieval gap is a bug, and knowing the difference matters more than forcing 9/9.

## Phase 2 — Structured extraction + fine-tuning ablation

### Claim extraction schema (`code/extract/schema.py`)
**Built:** `ClaimExtraction`, a Pydantic model with 6 fields (`claim_type` enum, `date_of_loss`, `cause`, `damaged_item`, `estimated_amount`, `policy_number`). Validated against 3 hand-written example narratives as a smoke test.
**Theory:** A Pydantic schema is a contract: it defines exactly what fields must exist, their types, and what's optional, then rejects anything that doesn't match. "Structured output" for an LLM means constraining free-text generation down to that contract — useful only if *every* consumer of the output (a prompt asking for JSON, and later a fine-tuned model producing JSON) is held to the identical contract, otherwise zero-shot and fine-tuned results aren't actually comparable.
**Here:** This schema is the single source of truth Phase 2's zero-shot baseline prompt and the eventual LoRA fine-tune's training target both have to conform to — so Step 2.5's accuracy comparison between them is measuring the same target, not two different ones.

### Real-world test anchor: 8 AFCA-sourced claims (`data/claims/afca_test.jsonl`)
**Built:** A synthetic-only test set grades zero-shot Claude against labels Claude itself invented — self-consistent by construction, not evidence of correctness against reality. Fixed by sourcing 8 real claim narratives from published AFCA (Australian Financial Complaints Authority) home-insurance determinations via secondary reporting (insurancenews.com.au, since afca.org.au itself blocks scripted fetches behind a Cloudflare JS challenge). Facts (cause, damage, dates, amounts) are tribunal-established; narratives were phrased by a different LLM (not Claude) from bare facts, closing the phrasing-circularity gap too, since the model graded (zero-shot Claude) shares no authorship with the test text. Conventions applied: `estimated_amount` = claimed (not awarded) figure; unknown-day dates default to 1st-of-month.
**Theory:** `ClaimExtraction` is deliberately insurer-agnostic (no insurer/policy-rules field) — it only tests narrative-to-structure parsing, not coverage decisions, so real AFCA cases work as test material even though Phase 1's PDS corpus doesn't cover the same insurers. AFCA case volume structurally excludes `glass_breakage`/`accidental_damage`/`other` (claims too small-dollar to ever reach a tribunal dispute), so those 3 categories stay synthetic-only by necessity, not oversight.
**Here:** Reported separately in `phase2_findings.md` alongside the synthetic-test aggregate, never blended into one metric — the synthetic test set has the per-class statistical power (larger n, full 9-class coverage) the AFCA set can't provide; the AFCA set has the real-world credibility the synthetic set can't provide. n=8, storm-heavy (5/8) — a real-world spot-check, not a per-class accuracy claim, same caveat as Phase 1's n=9 eval.

### storm/flood enum boundary resolved (`code/extract/schema.py`, `zero_shot.py`, `generate_synthetic.py`)
**Built:** Several heavy-rainfall cases (2 in the AFCA test set, a handful in the synthetic set) sat ambiguously between `storm` and `flood`. Resolved using the actual AU standard flood definition (Insurance Contracts Act, standard cover terms since 2012): `flood` = water escaping the normal confines of a named lake, river, creek, dam, or other natural watercourse; every other rain-caused loss (wind-driven rain, roof ingress, drainage overwhelm, surface pooling with no named watercourse) is `storm`, regardless of rainfall volume. Both AFCA rows resolve cleanly to `storm` under this rule (drainage/foundation overflow, no watercourse named) -- consistent with what AFCA itself ruled. Verified against the 150-example synthetic set: 12/17 `flood` rows correctly name a creek/river overflow, the remaining 5 are self-flagged ambiguous cases (not drift); spot-checked the 17 `storm` rows for the reverse mistake, found none.
**Theory:** "Flood" in everyday language just means "lots of water damage," which is why the zero-shot baseline (run before this fix) mis-called both ambiguous AFCA rows as `flood` -- a reasonable colloquial read, wrong under the specific legal definition that actually governs how AU policies are underwritten and worded. A domain-specific classification boundary needs the domain's actual technical definition encoded into the prompt, not left to a model's colloquial prior.
**Here:** Definition added to `ClaimType`'s source comment (human-readable, not seen by the model) and, operationally, to both `zero_shot.py`'s and `generate_synthetic.py`'s system prompts (schema JSON alone doesn't carry enum-level nuance to the model). Zero-shot results already collected (`outputs/zero_shot_results_afca.json`, `outputs/zero_shot_results.json`) predate this prompt fix and were not rerun -- the two AFCA misses are now understood as caused by the missing definition, not a genuine extraction failure; whether to rerun zero-shot with the fixed prompt is an open call, not yet made.

### `other` category bug: 7/16 rows were storm scenarios in disguise (`code/extract/generate_synthetic.py`)
**Built:** Spot-checking a formatted training row (`format_training_data.py`'s output) surfaced a `claim_type: "other"` row whose cause -- "tree branch fell during wind" -- was identical in pattern to 17 correctly-labeled `storm` rows elsewhere in the same 150-example set. Checked all 16 `other` rows: 7 were "tree branch fell during storm/wind" reworded six different ways, not genuinely distinct from `storm` at all. The other 9 were fine but repetitive (4 near-identical possum/wiring variants).
**Theory:** Same failure shape as the date-grounding bug -- the generation prompt named the target label (`claim_type: other`) without ever defining what "other" is *for* (a residual bucket excluding the 8 named categories), so the model fell back to its single most common home-insurance-claim template (wind/tree-branch) instead of picking a genuinely different kind of cause. A label with no definition attached gets filled with whatever's most probable under the model's prior, not what the label actually means.
**Here:** Fixed by adding an explicit exclusion rule to the prompt (`other` must not be storm/flood/fire/etc. in disguise; must be genuinely outside all 8 named categories) plus a diversity instruction. Rather than have Claude both write the fix and grade its own regenerated data -- the same author-is-reviewer risk flagged for the AFCA narratives -- a different LLM was given a self-contained version of the prompt (schema + all three fixes: date-grounding, storm/flood definition, other-exclusion) and asked to generate the 16 replacement rows independently. Reviewed with fresh eyes: 16/16 schema-valid, 0 groundedness failures (date/amount/policy), and critically, none described a storm/wind/tree-branch scenario -- genuine variety instead (termite, rats, four distinct ground-movement mechanisms, salt corrosion, concrete spalling, mortar decay, tile adhesion failure, truss hardware failure, dry rot, sinkhole). Spliced into `raw.jsonl` (`raw.jsonl.bak_before_other_fix` kept), re-split (still perfectly stratified: 11/2/3-4 per class), and `train_formatted.jsonl`/`val_formatted.jsonl` regenerated.

### Synthetic dataset generation bug: 79% of dates were ungrounded (`code/extract/generate_synthetic.py`)
**Built:** `generate_synthetic.py` generates 150 narrative+gold pairs via Claude (`effort: low`, no thinking overhead needed for this templated task), resumable, retry-once-then-skip on parse/validation failure. First run: 150/150 schema-valid, 0 skipped — looked clean. A human read of the spot-check sample then found narratives stating vague dates ("last month", "on the 14th") while `gold_extraction.date_of_loss` asserted a full invented year/month. Quantified: 118/150 (79%) of narratives never mentioned the year their own gold date asserted.
**Theory:** The prompt's general rule ("every fact in gold_extraction must be grounded in narrative") wasn't specific enough to survive contact with a separate instruction to write "realistic, conversational" prose — the model satisfied both instructions independently rather than reconciling them, since nothing tied the narrative's date-specificity to the gold field's required completeness. A general groundedness rule doesn't reliably constrain a specific field; the fix needed a field-specific instruction (state the full day+month+year explicitly, always) to close the gap. Caught only because a human read actual content against the stated rule — the pilot run beforehand had only checked schema-validity (`model_validate` passing), not groundedness, so it passed 3/3 while carrying the same latent bug.
**Here:** Regenerated (150/150 again, ~$0.60, `raw.jsonl.bak_missing_dates` kept for reference) with the fixed prompt. Re-verified all 5 fields, not just dates, this time: `date_of_loss` 0/150 ungrounded, `estimated_amount` 0/85, `policy_number` 0/100 (mechanical checks), `cause`/`damaged_item` clean on a 15-row manual read. One separate, lower-severity issue surfaced during that read and accepted rather than fixed: narratives show template repetition across otherwise-unrelated rows (e.g. two rows share the exact policy number `HM-2231987`), suggesting the generator draws from a narrower template space than 150 independent calls should produce — doesn't corrupt any gold label, but may understate how much real variation the LoRA fine-tune actually learns from.

### Zero-shot baseline (`code/extract/zero_shot.py`, `code/extract/eval.py`)
**Built:** `eval.py`'s `score()` grades each field appropriately to its type -- exact match for `claim_type`/`date_of_loss`/`policy_number`, token-set F1 for the two free-text fields (`cause`, `damaged_item`, since neither is actually list-shaped despite the checklist's "F1 for list-like fields" wording), 5%-tolerance match for `estimated_amount`. `zero_shot.py` calls Claude with the schema + rules as the system prompt, parses/validates the response, instruments cost and latency per call. Run on both test sets: synthetic `test.jsonl` (n=33) scored 0.915 overall, 0 parse failures, $0.09; real-world `afca_test.jsonl` (n=8) scored 0.853, 0 parse failures, $0.02. The two `claim_type` misses on the AFCA set were both the storm/flood boundary cases, later resolved by the definition fix above (not re-run afterward -- understood as stale, not a live bug).
**Theory:** A zero-division bug in `_token_f1` (two totally unrelated strings both hit `precision=0, recall=0`) was caught by the file's own `if __name__ == "__main__"` smoke test before it ever touched real data -- exactly what that kind of self-check is for.
**Here:** This is the number everything else in Phase 2 gets measured against.

### LoRA fine-tune: MPS allocator fragmentation, diagnosed and fixed (`code/extract/train_lora.py`)
**Built:** `train_lora.py` (co-written with the user, who wrote most of it directly) loads Qwen2.5-1.5B-Instruct, wraps it with a LoRA adapter (`q_proj`/`v_proj`, configurable rank/alpha), trains via `Trainer` with the loss masked to the JSON completion only. First real run appeared to work, then degraded across steps -- 11s/it → 51s/it → 189s/it, escalating, eventually taking the whole machine down (terminal blanked, system-wide lag) before it was killed.
**Theory:** Batch size 1 (chosen to avoid writing a padding collator) means every step hands MPS a differently-shaped tensor. MPS's memory allocator is less mature than CUDA's and fragments under exactly that pattern -- each new shape can force a fresh allocation instead of reusing freed memory, compounding step over step until the system runs out of usable memory. A `caffeinate`-related display-sleep theory was tested first (ruled out: the escalation pattern doesn't match a one-time throttling event) before landing on the allocator explanation.
**Here:** Fixed with a `TrainerCallback` calling `torch.mps.empty_cache()` after every step -- forces MPS to release what it's holding before the next differently-shaped tensor arrives, without needing the heavier fix (padding every example to a fixed length, which would have cost real compute on every step). Confirmed: r=8 completed cleanly afterward, 39/39 steps, stable ~17s/it, no further escalation. Also measured (not guessed) the real max token length across the dataset (804) and pre-tokenized once in `__init__` instead of per-epoch -- both cheap, safe speedups layered on top once the fragmentation was actually fixed.

### Rank sweep: r=4 wins, no capacity ceiling (`code/extract/lora_infer.py`, `outputs/phase2_findings.md`)
**Built:** `lora_infer.py` runs a saved adapter over a test set the same way `zero_shot.py` does (same instruction, same parsing/validation, same `eval.py` scoring), so LoRA and zero-shot numbers are directly comparable. Swept `r ∈ {4, 8, 16}`: r=4 won outright -- best or tied-best on every field, 0/33 parse failures, cheapest to train. Higher rank measurably hurt (r=16 worst). Confirms the original small-data hypothesis: 99 training examples has nothing for extra adapter capacity to use.
**Theory:** Comparing r=4 vs. zero-shot on both test sets shows the gap is concentrated specifically in the two free-text fields (`cause`, `damaged_item`) -- the structured fields (`claim_type`, `estimated_amount`, `policy_number`) match zero-shot exactly or near-exactly on both the synthetic and real-world sets. That's a data-volume signature, not a capacity signature (matches the rank sweep's own finding that less capacity did better) -- more motivation to add more/better training data before ever trying a bigger base model, which is exactly why the planned Llama-3.2-3B escalation was not triggered.
**Here:** Full comparison and the resulting hybrid recommendation written to `outputs/phase2_findings.md`.

### `extract_fields()` hybrid wiring (`code/extract/extract_fields.py`)
**Built:** One function, `extract_fields(claim_text: str) -> ClaimExtraction`, matching the interface Phase 3's tool is meant to wrap. Tries the LoRA r=4 adapter first (free, fast, cached across calls the same way `rag/generate.py`'s `_client()` avoids rebuilding a client every call); falls back to a live Claude call if the adapter's output fails to parse/validate; raises if both fail rather than returning something fake. Co-written with the user, who wrote most of it directly.
**Theory:** Two real bugs caught by actually running it, not just reading it: a name collision (`lora_infer.py` and `zero_shot.py` both export a function called `extract_one`, with different signatures -- importing both unaliased made the second import silently shadow the first) and a copy-paste bug (the Claude-fallback branch checked `lora_result is not None` instead of `claude_result is not None`, which meant the fallback could never actually succeed even when Claude returned a valid result). Both verified fixed by actually forcing the failure path (monkeypatching the LoRA call to fail) and confirming Claude genuinely took over, not just by re-reading the code.
**Here:** This is the function Phase 3's `extract_fields` tool will call directly -- Phase 2 is now fully wired end to end, schema through to a working hybrid extraction function.

## Errors & Issues Faced

Quick-reference log: what broke, why, how it was resolved. Full theory for the starred (*) items is in the matching entry above.

1. **`response.content[0].text` crashed with `AttributeError`** on the first real generation call. *Cause:* Sonnet 5 runs adaptive thinking by default, so `content[0]` can be a `ThinkingBlock`, not the text block. *Fix:* find the block by `type == "text"` instead of assuming index 0.
2. **Workspace-identity-linked API key rejected with 400** ("anthropic-workspace-id is required").* *Cause:* this org's key requires the request to declare which workspace it spends against; the SDK only auto-attaches that header on a separate WIF/Bearer credential path, not a plain `api_key=` client. *Fix:* read `ANTHROPIC_WORKSPACE_ID` manually and pass it via `default_headers`.
3. **RRF retrieval bug found via Step 1.7 eval** (RAA flood question returned "not enough information" when the policy clearly covers it).* *Cause:* the correct chunk was BM25's #1 pick but fell just outside the fusion pool's top-15 cutoff, so it got zero credit from the vector ranker. *Fix:* widened `RETRIEVAL_POOL` 15→30 (global constant, verified it didn't just paper over the one test case).
4. **`NameError: urllib` after refactoring `discover_sources.py`** to use a shared HTTP helper. *Cause:* removed the `import urllib.request` line, not realizing `urljoin(...)` was being called as `urllib.request.urljoin` — working only because `urllib.request` transitively re-exports `urljoin` from `urllib.parse` internally. *Fix:* import `urljoin` explicitly from its real location, `urllib.parse`.
5. **Possible silent crash on refusal/truncated responses**, caught by `/code-review` before it ever happened in practice: `next(... for ...)` with no default raises `StopIteration` if a response has no text block at all (safety refusal, or cut off before any text). *Fix:* explicit `None` default + a clear `RuntimeError` instead.
